# mcp-toolpacks

**按用途给 MCP 工具分组，而不是按服务器。一组一个开关。**

[English](README.en.md) · [数据格式](SPEC.md) · [为什么这么设计](#七条非显然的洞见)

---

## 问题

MCP 服务器是按**「谁提供的」**打包的，不是按**「你现在要干什么」**打包的。

一个服务器经常把四五件互不相干的事塞在一起：

```
github server
├── 代码     get_file · search_code · list_commits
├── issue    list_issues · create_issue · close_issue · comment_issue
├── PR       create_pull_request · review_pull_request · merge_pull_request
└── 通知     list_notifications · mark_notification_read
```

你此刻只想问一个关于代码的问题。但客户端给你的开关**只有一个**：整台开，或者整台关。

于是你四个全开。模型现在有能力合并你的 PR —— 它只是碰巧没这么做。

这不是某个服务器的毛病，是这个粒度的毛病。**分组应该跟着意图走。**

## 代价

工具定义（名字 + 描述 + 参数 schema）是**每一轮请求都原样重发**的。它们不是「用的时候再取」，是常驻在上下文里的。

粗算一下：

| | |
|---|---|
| 一个工具的定义 | 约 150–300 token |
| 一个 46 个工具的服务器 | 约 7,000–14,000 token |
| 你每天发 200 轮 | 那就是**每天**上百万 token |

而且这个开销跟**你有没有用到**完全无关。它只跟「开着几个工具」有关。

拿你自己的服务器数一数：**工具数 × 200 ≈ 每轮白烧的 token**。

## 解法

一个 **pack**：一组按用途命名的工具引用，配一个开关。

```json
{
  "id": "issues",
  "title": "Working issues",
  "desc": "读、提、关、评论 issue",
  "mcpTools": {
    "github": ["list_issues", "create_issue", "close_issue", "comment_issue"]
  }
}
```

关键在 `mcpTools` 的键是**服务器名**，值是**这台服务器上我要的那几个工具名**。

这就是全部的把戏：**你按工具名引用，而不按服务器引用** —— 因为服务器那个分组，一开始就是错的。

于是「只开 issue、不开 PR」变成了一件能表达的事。而且同一个 `github` 上可以同时挂好几个包，互不打架。

完整格式见 [SPEC.md](SPEC.md)，能跑的示例见 [`examples/packs.example.json`](examples/packs.example.json)。

## 七条非显然的洞见

前面是背景。**这一节才是这个仓库存在的理由。**

下面每一条，都是我们踩过之后才明白的。写下来，是为了让你不用再踩一遍。

### 1. 开一个包，不是「把它的成员打开」

最自然的那版实现是：

> 开包 = 把成员打开；关包 = 把成员关掉。

**这是错的**，而且错得很隐蔽。

真实情况是：服务器上的工具**默认几乎全是开着的**，真正的总闸是「这台服务器挂没挂上」。所以「把成员打开」只是把本来就开着的又打开了一遍，什么都没改变 —— 你打开「邮件包」，结果同事塞在同一台服务器上的那个小游戏也跟着来了，因为它俩本来就都是 `enable: true`。

正确的规则是**盯着结果，而不是盯着增量**：

```
1. 先算出，这次改动之后，有哪些包是开着的
2. 只看【这个包点名的】那几台服务器 —— 别的服务器一概不动
3. 对每台被点名的服务器：
     该开的 = 所有「开着的、且碰这台服务器」的包的并集
     不在并集里的，全部关掉
4. 一个工具都不剩的服务器，从挂载列表里摘掉
```

第 2 条不能省。少了它，「开邮件包」会顺手把别的服务器也关了 —— 那不是用户按的那个键该干的事。

第 3 条有个**必须知道的副作用**：因为是按并集**覆盖**，所以被包盖住的服务器上，**没被任何包点名的工具会被强制关掉**。用户要是在别的设置页里手工开过某个工具，碰一下这个包就没了。

这是故意的（「关着」才是默认值）。但代价是 —— 见第 5 条。

### 2. 静默失效是这里最大的敌人

这套东西坏了，**界面上看不出来**。

- 该开的没开 → 用户觉得「这功能怎么不好使」。
- 该关的没关 → **每一轮请求都在多花钱，而且没有任何一个界面会告诉他**。

第二种更糟。所以这个仓库里，凡是「猜不准」的地方，一律选择**不猜**：

- 名字对不上 → 什么都不动（见第 3 条）
- 服务器找不到 → 画在卡片上
- 工具没被任何包认领 → 有测试专门盯着

### 3. 名字对不上时，一个字节都不许动

这是真出过事故的一条。

客户端的工具清单是个**缓存** —— 是它上一次 `tools/list` 抄下来的，不是实时的。服务器上新加了工具，而客户端还没同步的时候：

- 包点名的工具名字，一个都对不上
- 第 1 条的算法只认名字 ⇒ 并集算出来是**空的**
- ⇒ 那台服务器上的工具**全被关掉，连服务器一起被摘下来**

用户看到的是「开关点了没反应」。实际发生的是**那台服务器上的所有功能当场失灵**，而且是在对话中途。

正确的做法是在入口处就拦住：

```ts
if (enable && unavailable(state, pack).length > 0) {
  return { state, blocked: unavailable(state, pack) }  // 原样返回，什么都没动
}
```

**只拦开启方向。** 关闭方向必须永远可用 —— 万一服务器以后真的永久删掉了某个工具，那是用户唯一的退路。

配套的操作流程也很重要：

> 用户拨开关 → 先跟服务器同步一次工具清单 → 再复检
> → 名字还是对不上 → **中止，并告诉他缺哪几个** —— 不是静默放过，也不是硬着头皮算

### 4. 「这个包开着没开」要算出来，不要存

不要在开关旁边存一个 boolean。

> 包开着 ⟺ 它的成员**全部**都开着

存一个布尔值，就是「开关说有、实际没有」这类账的源头 —— 而你通常要等到几个月后查账单才发现。

算出来的话，这类 bug **在结构上就不存在**。

> ⚠️ 没有「部分开」这个状态。只要有一个成员没满足，就算关着。
> 好处同样是：不另存状态，就不会对不上账。

顺带一提，这个判据是**按包**的：同一个服务器上挂着两个包，两个各自都算「开着」，它们不争抢共用的那个工具。

### 5. 「说好了要关的」要有一张显式名单

接着第 1 条的副作用说。

既然没被点名的工具会被强制关掉，那么**「哪个包也没提它」就等于「默默关掉」**。

三个月后没人说得清那到底是个决定，还是个疏漏。

所以要有一张显式的表：

```ts
const DISABLED = {
  github: ['list_notifications', 'mark_notification_read'],
}
// 理由写在这里 ↑ 而不是写在某个人脑子里：
// 客户端自己会渲染通知，这两个工具是重复的，还要多花 ~400 token/轮
```

**加东西进来必须写理由。** 不写下来，它就跟坏了没区别。

### 6. 这套东西错了在界面上看不出来 ⇒ 必须写测试

再说一遍，因为它是这七条里唯一一条「不做就一定出事」的：**这些失效是无声的**。

所以必须把判据钉成测试，尤其是「并集」那条 —— 同时开两个包时谁也不能把谁挤掉。

[`test/resolve.test.ts`](test/resolve.test.ts) 里那 22 条就是干这个的。每一条都**以它防的那个 bug 命名**，不是以它调用的那个函数命名。

另外还有一条测试钉住的是**表本身**：

```ts
it('每台服务器上的每个工具，都被某个包认领、或者被显式列为关闭', ...)
```

这条挂了，就说明有工具正在被默默关掉。

### 7. 一次写完

「这台服务器挂了没」和「服务器上开哪些工具」是**两处状态**。它们必须**一次写完**。

分开写的话，中间会有一个「工具开了、但服务器还没挂上」的瞬间。用户不幸正好在那时候发消息，就会拿到一个说不清的结果。

所以 `resolve()` **不返回增量**，它返回**一整份新的 `AppState`**。调用的那一边只负责落一次盘。

## 上线前先做这五件事

1. **把每个工具都归到一个包里，或者写进关闭名单。**
   漏一个，它就会在用户碰那个服务器上的任何一个包时，被无声地关掉。
2. **给「关闭名单」的每一条写理由。** 写在代码注释里，不是写在某个人脑子里。
3. **把并集语义写成测试。** 至少覆盖：两个包同时开、关掉其中一个、重叠的工具。
4. **拨开关之前先同步工具清单，并处理 `blocked`。** 不要静默放过。
5. **整个新状态一次写完。** 不要分两次保存。

## 实现

```
src/
├── types.ts      数据模型 —— 朴素 interface，没有框架、没有 class、不用你生成 id
├── resolve.ts    ★ 核心：resolve() / isOn() / unavailable()
└── validate.ts   validate() —— 健康检查，把「无声失效」变成一条能断言的报告
```

没有运行时依赖。`resolve()` 大约八十行，注释解释了每一个分支 —— 移植到任何语言都是十来分钟的事。

```bash
npm install
npm test          # 22 条，全绿
npm run typecheck
```

`test/fixtures.ts` 里的包表**直接读 `examples/packs.example.json`** —— 这样文档和测试不会各说各话。

界面长什么样，见 [`examples/react/PackCardList.tsx`](examples/react/PackCardList.tsx)（单文件，没有 CSS 依赖）。
